# Helix Remote Backend Reference Architecture

This document specifies the backend reference architecture for Helix Remote, resolving tasks P8-019 through P8-034.

---

## 1. Backend Language and Framework (P8-019)
*   **Approved Technology Stack**: **Go (Golang)** with the **Chi router** for routing, and standard libraries for WebSocket handling (e.g., `gorilla/websocket` or `nhooyr/websocket`).
*   **Rationale**: Go provides outstanding concurrency throughput, very low memory footprint, strict compile-time types, excellent support for persistent HTTP/2 and WebSocket connections, and compiles to a single binary perfect for our modular monolith deployment.

## 2. Backend Module Boundaries (P8-020)
The backend is structured as a **Modular Monolith** to prevent spaghetti code while avoiding the operational overhead of microservices:
```
helix_remote_backend/
├── cmd/
│   └── server/                 # Application entry point & composition root
├── internal/
│   ├── platform/               # Database pool, Redis client, logger, metrics
│   └── modules/
│       ├── accounts/           # Account registration, device link, auth tokens
│       ├── keys/               # Identity keys, prekeys (Signal protocol keys directory)
│       ├── contacts/           # Friend requests, contact list, blocking
│       ├── conversations/      # Direct/Group conversations & memberships
│       ├── messaging/          # Delivery queue, sync mailbox, push triggers
│       ├── attachments/        # Pre-signed S3 URL generation & validation
│       └── call_signaling/     # Ephemeral WebRTC signaling gateway
```
Modules communicate with each other *only* through defined Go interfaces (Contracts), never by directly accessing another module's internal database models.

## 3. Database Ownership per Module (P8-021)
To enable future microservices extraction if needed, each module owns its database schema tables. No cross-module joins are allowed.
*   **Accounts/Devices Module**: Owns `accounts`, `devices`, `sessions`.
*   **Keys Module**: Owns `prekey_bundles`, `one_time_prekeys`.
*   **Contacts Module**: Owns `friendships`, `blocks`.
*   **Conversations Module**: Owns `conversations`, `participants`.
*   **Messaging Module**: Owns `messages`, `outbox`, `sync_cursors`.
*   **Attachments Module**: Owns `attachments`.

## 4. Transaction Boundaries (P8-022)
*   Transactions must start and finish within a single module's boundary.
*   If an operation spans multiple modules (e.g. creating a conversation and dispatching a welcome message), it must use the **Transactional Outbox Pattern** or application-level orchestration rather than spanning SQL transactions across module boundaries.

## 5. Transactional Outbox (P8-023)
*   **Pattern**: To guarantee reliable messaging and event dispatch without distributed transactions, modules write business events to an `outbox` table in the same local SQL transaction.
*   **Worker**: A background Go worker polls the `outbox` table, publishes events (like FCM pushes or WebSocket broadcasts), and marks the outbox rows as sent.

## 6. Idempotency Strategy (P8-024)
*   All mutations (e.g. sending a message, accepting a contact request) must include an `idempotency_key` (UUID v4) generated by the client.
*   The server checks a Redis-backed or DB-backed idempotency registry. If the key exists, the server returns the cached result without repeating the operation.

## 7. Retry and Dead-Letter Queue (DLQ) Strategy (P8-025)
*   **Outbox Retries**: If the background worker fails to dispatch an outbox event, it retries with exponential backoff (e.g., 2s, 4s, 8s, up to 10 iterations).
*   **DLQ**: If retries exceed the limit, the event is moved to a `dead_letter_events` table for manual administrator auditing and alerts are sent via monitoring.

## 8. Rate Limiting (P8-026)
*   Enforced at the API Gateway level using Redis-backed Token Bucket algorithm.
*   **Limits**:
    *   `/api/v1/auth/*` (Login, Register): 5 requests per minute per IP.
    *   WebSocket connections: 2 connection attempts per minute per account.
    *   API message send: 60 requests per minute per account.

## 9. Ephemeral Presence (P8-027)
*   **Rule**: User presence (Online/Offline) and typing indicators are strictly ephemeral state.
*   **Storage**: Stored in RAM (Redis Pub/Sub or Key-Value with a 30-second TTL), never written to Postgres disk.
*   **Clean Up**: If a WebSocket disconnects, the server automatically publishes an offline event and clears the typing state.

## 10. Attachment Lifecycle (P8-028)
*   **Upload**: Client requests upload URL -> Server issues S3 pre-signed POST with a tight expiration (15 minutes) and strict size constraints.
*   **Orphan Clean-up**: If a file is uploaded to S3 but not referenced in any sent message within 24 hours, an S3 Lifecycle Policy automatically deletes the file.
*   **Retention**: S3 objects are persisted until the corresponding message is deleted by all conversation participants, at which point the client signals deletion to S3 via the server.

## 11. Backup and Restore (P8-029)
*   **Backup**: Clients upload encrypted database snapshots. The server stores these as opaque binary objects in a dedicated secure backup S3 bucket.
*   **Keys**: The backup key is derived client-side via PBKDF2/Argon2. The server never receives or stores this key.
*   **Restore**: Client downloads the opaque blob and performs client-side decryption.

## 12. Disaster Recovery Targets (P8-030)
*   **Recovery Point Objective (RPO)**: Under 1 hour (via Postgres WAL archiving to S3 every 15 minutes).
*   **Recovery Time Objective (RTO)**: Under 4 hours (via automated infrastructure deployment scripts and DB restore routines).

## 13. Observability without Content Logging (P8-031)
*   **Strict Security Rule**: Log messages must *never* contain message text, file names, attachment keys, password hashes, or session tokens.
*   **Tracing**: Request tracing via OpenTelemetry with unique `correlation_id` across REST calls and WebSocket frames.
*   **Metrics**: Prometheus monitors connection count, API latencies, active WebSockets, rate-limit triggers, and database pool capacity.

## 14. Staging and Production Isolation (P8-032)
*   Production and Staging run in entirely separate AWS/GCP accounts or isolated VPC networks.
*   No database links, credentials, or encryption keys are shared between environments. Staging uses mock data and mock Apple/Google push credentials.

## 15. Data-Region Policy (P8-033)
*   To comply with regional data privacy laws (e.g. GDPR), users can select their data residency region at registration time.
*   Server endpoints route traffic to regional database instances and regional S3 buckets based on the account residency configuration.

## 16. Operational Admin Access and Approval Controls (P8-034)
*   No developer has direct read/write access to production databases.
*   Administrative actions (e.g., account suspension, abuse report review) require authentication through a multi-factor-auth admin panel with all access audit logs sent to a tamper-proof write-once system.
