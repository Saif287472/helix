# Orbit: the Flutter port plan

Status: agreed 2026-10-17 (decisions below). Nothing in `helix_remote/` changes
until Part B, and Part B starts only when you say so.

The job has two parts:
- **Part A:** turn the HTML prototype into Flutter screens that run on fake
  data, outside the main app.
- **Part B:** move those screens into the main app, connect them to the real
  data, and delete the old UI.

## Why the last attempt went wrong, and what is different now

An agent was given the HTML and told to build it into the main app. That
went wrong for four reasons.

1. **It redesigned and rewired at the same time, inside a working app.**
   Every screen had to be redrawn and reconnected at once. Keeping the app
   working always wins that fight, so the design lost.
2. **The HTML was treated as a picture, not a specification.** Sizes,
   spacing and colours were guessed. Parts the agent didn't understand were
   invented.
3. **There was no way to check.** "Looks roughly right" passed because
   nobody put the two side by side.
4. **It was one huge task.** There was no point where you could stop it
   early.

This plan answers each of these:

1. **Drawing and wiring are separate.** Part A draws the UI with no backend
   at all. Part B wires it in, and no design changes are allowed during
   Part B.
2. **The prototype is the specification.**
   - Colours, fonts and shapes are generated from the same source as the
     CSS (`tools/themes.py`), so nothing is retyped.
   - Anything that isn't in the prototype isn't built. Anything that can't
     be matched is written in `DEVIATIONS.md` for you to approve.
3. **Every screen is compared automatically.** Each of the 181 prototype
   screens is screenshotted in HTML and in Flutter. A compare page shows the
   two side by side, with an overlay slider and a difference score.
4. **The work is done in small batches.** Each batch ends with your review on
   the compare page, and nothing moves on until you approve.

## Decisions (2026-10-17)

| Question | Decision |
|---|---|
| How the screens reach the app | One shared package, `orbit_ui`, used by the preview and the app. Part B adds connectors; no screen is copied or retyped. |
| What to finish before porting | The wide Windows layout, and the older-style pages restyled in the You style (Phase 0). |
| High contrast | No special theme. The chosen theme always shows. |
| Checkpoints | After each batch you approve, commit all uncommitted work (your usual rule), never push. |

## The shape of the code

```

  packages/orbit_ui/              the design system AND every screen
    lib/src/theme/                OrbitTokens (ThemeExtension), 8 themes
                                  (GENERATED by tools/themes.py), fonts, icons
    lib/src/components/           avatar, chat row, dock, bubble, composer,
                                  sheets, fields... (from the CSS and ui.js/kit.js)
    lib/src/models/               view models (see "Reusing the app's view models")
    lib/src/features/<feature>/
      chats_contract.dart         ChatsModel + ChatsActions: the contract
      chats_screen.dart           the screen: model in, actions out
    fonts/                        the bundled theme fonts (all OFL)
    test/                         widget tests, rule tests, screenshot tests
  apps/orbit_preview/             the Flutter twin of the HTML viewer
    lib/index.dart                the same screen list, with the same keys
    lib/fake/                     fake data (from data.js) and fake actions

  tools/compare/                  screenshots both sides, builds the compare page
```

### The one rule that makes Part B safe

A screen never reads a provider, the database, the router or the engine. It
gets two things:
- **A model:** plain immutable values.
- **An actions object:** callbacks such as `openChat(id)`, `archive(ids)` and
  `send(text)`.

Some state stays inside the widget, because only the screen needs it:
- which sheet is open,
- scroll position,
- the text being typed,
- animations.

The preview app gives a screen fake models and fake actions. The main app
will give the same screen real ones.

Platform-heavy parts come in as **slots** that the app fills: the camera, the
QR scanner, video, call video and the file picker. In the preview, the slots
show placeholders. The current app already works this way in places, for
example `ChatsTab.detailBuilder`.

### Why one shared package, not a copy

In Part B, `orbit_ui` moves into `helix_remote/packages/` unchanged. The
preview and the app then use the very same screen files, so nothing is
retyped and nothing drifts. The preview keeps working afterwards as the place
to try design changes on fake data.

In the main app:
- Each `features/<x>/presentation/` folder becomes thin connectors. A
  connector watches the existing providers, builds the model, and maps the
  actions to the existing notifiers and routes.
- The application layer, about 15,000 lines that are already tested, stays.

### Reusing the app's view models

The app's mappers (`chat_list_mapper`, `message_mapper`, `timeline_builder`
and others) already produce `HelixChatListItem`, `HelixMessage`,
`HelixTimelineItem` and so on, from `helix_remote_ui/view_models.dart`. The
prototype's `data.js` was shaped like those models.

- `orbit_ui` starts from a copy of `view_models.dart` with the same class
  names. New fields are added with defaults; nothing is removed or renamed.
  That way the existing mappers feed the new screens without being
  rewritten.
- At the start of Part B, the models move into `orbit_ui`, and
  `helix_remote_ui` re-exports them. The old and new screens then share the
  same types while the features are switched over one at a time.

## Part A: build the UI alone

### Phase 0: freeze the prototype (it is the specification)

1. Finish what isn't designed yet. Otherwise the port has to invent it, which
   is exactly what went wrong last time.
   - **The wide Windows layout.** The app already shows two panes on wide
     windows: the list on the left, the chat on the right
     (`HelixBreakpoints.medium`). The prototype has no design for this.
   - **The older-style pages, restyled in the You style:** Help and about,
     Advanced, Blocked, Change password, Delete account, Restore, Send to your
     devices, Recovery backup, Security activity and Link a device.
   - **High contrast: decided, no special theme.** The chosen theme always
     shows, even when the phone asks for high contrast. All eight themes
     already pass the contrast minimums. In Part B the app's
     `highContrastTheme` is removed.
2. Make the prototype measurable:
   - A bare mode (`?bare&theme=arcade#group`) that draws only the phone
     screen at 412×866, for screenshots.
   - A manifest, `screens.json`, exported from the prototype's own index.
     Each entry has its key, label, group, screen, parameters, the screens
     underneath it, and the interactions it has (swipe, long-press,
     hold-to-record, and so on). This is the port's checklist.
3. Freeze: the prototype is versioned. Any later design change gets a dated
   entry in `SCREENS.md`, and the affected screens are compared again.

### Phase 1: contracts and the gap list (no UI yet)

For each feature, write the contract file (the model and actions classes).
It comes from reading three things side by side:
1. **The prototype screen:** what the design shows and does.
2. **The app's current screen:** what it shows and does today, including
   loading, errors, empty states, permission prompts, confirmation dialogs
   and failure messages.
3. **The app's application layer:** what data and operations exist.

Every field and action gets a tag:

| Tag | Meaning | Example |
|---|---|---|
| **have** | the app already provides it | chat list items, delivery ticks |
| **derive** | the app can compute it from what it has | Unread/Groups filters, checkup score, tile status lines |
| **local** | a new setting kept on the phone | the chosen theme |
| **new backend** | needs engine or server work | to confirm: sharing your profile photo with people (today the photo stays on your phone), the `/u/<name>` share link, "free up this chat's media" |

The phase produces two lists for you:
- **New backend items.** For each one you decide: build it in Part B (the
  normal `helix-feature` process), hide it until later, or drop it.
- **Things the app does that the prototype doesn't show.** These are states
  and messages the HTML never drew. For each one you decide: add it to the
  design (back to Phase 0 for that screen), or drop it.

**Review 1:** the contracts and both lists.

### Phase 2: the foundation

- **The Flutter workspace** `orbit/flutter/`, on the same Flutter and Dart
  versions and the same lint rules as `helix_remote/`.
- **The theme generator.** `tools/themes.py` also writes
  `orbit_themes.g.dart`. CSS and Dart come from one table, and the contrast
  check covers both.
- **Fonts.** All 14 families are bundled (all OFL), with the app size cost
  measured and reported. Icons come from `phosphor_flutter` (light, regular,
  duotone, bold, fill).
- **Theme effects** as painters:
  - the chat patterns (dot grid, neon grid, contour lines, grain, hearts),
  - Arcade glow,
  - Terminal scanlines and cursor,
  - Papyrus double rules and ❦,
  - Field stripes.
- **The preview app shell.** Screen index, theme picker, the phone frame at
  412×866, and the same keys as the prototype. It runs on Windows (and on
  your phone with `flutter run`).
- **The compare tool:**
  - Headless Chrome screenshots the prototype's bare mode.
  - A Flutter test renders each key at 412×866 with the real fonts loaded.
  - The compare page shows both sides with an overlay slider, a difference
    heat map and a score per screen, worst first.
  - Text renders slightly differently in Chrome and Flutter, so the score
    flags screens for your eye rather than demanding zero.

**Review 2:** the theme gallery in all eight themes, plus the compare tool
working on a first screen.

### Phase 3: the components

Components are ported in dependency order, each with a gallery page showing
every state in all eight themes. The app's rules carry over as tests in
`orbit_ui`:
- every icon button has a tooltip,
- tap targets are at least 48 px,
- text scaling is never clamped,
- screen-reader labels are present,
- no colour is typed into a widget (tokens only),
- list items skip rebuilds when their model is equal (the app's performance
  budgets).

**Review 3:** the component gallery.

### Phase 4: the screens, batch by batch

Each batch goes through the same steps: build, run the compare page, your
review, fixes, your approval, then a checkpoint (a commit of all
uncommitted work). The batches, in order:

1. Sign-in: phone, code, password, name, restore, link a device, reset, lock.
2. Home: the Chats and Calls tabs, the dock, filters, search, selection,
   swipe, archived chats and the dial pad.
3. Conversation: the timeline, every message kind, every composer state,
   message actions and in-chat search.
4. The conversation's pages: forward, message info, the media viewer, send
   files, shared media and chat settings.
5. Calls: every call state and the call detail.
6. People: the contact page, safety number, scan and people search.
7. Groups.
8. You: the profile editor, the topic pages and Appearance.
9. The remaining settings pages, devices and backup.
10. The wide Windows layout.

A screen is done when:
- every one of its keys passes the compare, both by score and by your eye;
- it works in all eight themes;
- its interactions work in the preview;
- its widget tests pass;
- every difference from the prototype is in `DEVIATIONS.md` and approved.

**Review 4:** the whole preview, start to finish. Part A ends here.

## Part B: put it in the app (only when you say so)

Part B happens in a separate worktree and branch (`J:/wt/orbit`, branch
`orbit-ui`), so `main` and your current work are untouched until you decide
to merge. Production is never stopped or redeployed.

1. **Move the package in.**
   - `orbit_ui` goes to `helix_remote/packages/orbit_ui` and is added to
     `v2PackageDependencies`.
   - The presentation import rule allows `orbit_ui`.
   - The dependency documents get entries for `phosphor_flutter` and the
     fonts.
   - The view models move as described in "Reusing the app's view models".
2. **Switch one feature at a time**, in the Phase 4 order. For each feature:
   - Rewrite `features/<x>/presentation/` as connectors.
   - Build its "derive" and "local" items in `application/`.
   - Build the "new backend" items you approved, through `helix-feature`.
   - Update its widget tests. About 30 test files and roughly 1,200 finders
     refer to today's text and icons.
   - Delete the old screens.
   - Run `flutter analyze` and every app test, and get them green before the
     next feature.
3. **App-wide changes:**
   - The chosen theme is stored in local settings and drives `MaterialApp`.
   - The "light theme only" rule is retired: AGENTS.md and
     `product_rules_test`. `highContrastTheme` is removed, so the chosen theme
     always shows.
   - The app is called Orbit: the app name, the window title and the icon
     from `orbit-mark.svg`.
4. **Clean up.** Delete `helix_remote_ui` once nothing imports it, along with
   its gallery and golden tests. Update AGENTS.md, the `FEATURE.md` files and
   the architecture documents.
5. **Verify.**
   - Run the full gate (`scripts/verify.ps1`) and the journey tests.
   - You build the APK and try it on your phone, and run it on Windows.
6. **Merge and commit** only when you say.

Part B must never:
- **Change a design.** Any visual change goes back to the preview first and
  is compared again.
- **Change application logic** beyond the gap items you approved.
- **Touch the server, protocol or crypto** unless an approved gap item needs
  it.

## Rules for every agent on this work

These rules are copied into `orbit/flutter/AGENTS.md`.

- **The prototype is the specification.** Before building a screen, read its
  JS and the CSS rules it uses. Sizes, spacing, corners, font sizes and
  colours come from there, and from tokens, never from typed values.
- **Don't invent.** If something isn't in the prototype, stop and ask. If
  something can't be matched in Flutter, write it in `DEVIATIONS.md` and ask.
- **Use the same screen keys** as the prototype.
- **Stay out of the app until Part B.** Nothing under `helix_remote/` changes
  before Part B. Nothing under `helix_local/` changes, ever.
- **A batch isn't done** until its compare page is clean and you have
  approved it.
- **Keep batches small** and stop at each review.
