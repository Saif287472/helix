## What is sound

- **Opening cannot be downgraded**: a plaintext file is refused before opening,
  the key is applied as a hex literal and checked by `cipher_status` plus a
  `sqlite_master` probe, a wrong key surfaces as `DbEncryptionException` (not a
  bare sqlite error), and `DatabaseKey` prints redacted and compares in constant
  time ([opening.dart:1-206](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/opening.dart#L1),
  [database.dart:197-224](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/database.dart#L197)).
- **At-rest hygiene is set on every connection**: WAL, `synchronous=NORMAL`,
  a 4 MiB journal limit, 5 s `busy_timeout` (two engines on one file),
  `secure_delete`, `foreign_keys`
  ([opening.dart:150-163](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/opening.dart#L150)).
  `wipeAll` checkpoints, vacuums and checkpoints again; the test proves deleted
  bytes are gone *and* proves the assertion can fail without `secure_delete`
  ([wipe_test.dart:41-109](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/test/wipe_test.dart#L41)).
- **Migrations are actually tested**: a fresh database is validated against the
  schema-4 dump, every from→to pair is migrated and validated, and each step has
  a data-integrity test that keeps rows and proves the new revision column is
  usable ([migration_test.dart:24-193](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/test/drift/helix/migration_test.dart#L24)).
  `from1To2` creates frozen v2 entities, not live table classes.
- **The compare-and-set is safe against the second engine.** drift 2.34's
  SQLite delegate begins transactions with `BEGIN IMMEDIATE` on purpose, so a
  read-then-write transaction never upgrades a stale snapshot: the losing writer
  waits (busy_timeout) and then reads the committed revision, and
  `saveSessions` / `saveOwnSenderKey` return false instead of raising
  `SQLITE_BUSY_SNAPSHOT`
  ([drift-2.34.0/lib/src/sqlite3/database.dart:68-75](file:///C:/Users/Hasan/AppData/Local/Pub/Cache/hosted/pub.dev/drift-2.34.0/lib/src/sqlite3/database.dart#L68),

## Findings

### AUD-10-1 Bulk maintenance deletes bind every row id in one statement; past SQLite's parameter limit the delete throws and maintenance stops rescheduling

**Severity:** P3
**Confidence:** likely
**Where:** [messages_dao.dart:184-196](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L184)
(`removeExpired` reads *every* due row id first), then
[messages_dao.dart:165-181](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L165)
(binds the list twice, at [`:171`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L171)
and [`:176`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L176));
[messages_dao.dart:578-609](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L578)
(`detachLocalMedia` binds every found attachment id at
[`:601`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L601));
[history_store.dart:85-96](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L85)
(`receiptsFor`, same shape at
[`:90`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L90)).
Consumers: [maintenance.dart:57](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/maintenance.dart#L57)
and [maintenance.dart:110-116](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/maintenance.dart#L110).

**What:** A set-valued delete is expressed as a Dart list of ids inside one
`IN (?, ?, …)`. SQLite's default build limit is 32,766 host parameters per
statement; above it the statement fails with "too many SQL variables" and the
whole transaction rolls back. `removeExpired` is the reachable case because it
selects *all* due rows before deleting any, so one unusually large due set is
enough.

**Trigger:** more than 32,766 messages whose disappearing timer has run out
before the next maintenance pass. Incoming messages get `expires_at` only when
drawn (one at a time, [read_tracker.dart:86-98](file:///J:/Projects/helix/helix_remote/app/lib/features/conversation/application/read_tracker.dart#L86)),
so the realistic paths are a very large outgoing burst in one timed chat and a
"clear storage"/media sweep over a chat with tens of thousands of downloaded
files ([detachLocalMedia](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L578));
`history_store.dart` is reachable only with an export page above the limit
(today's pages are far smaller).

**Evidence:** the ids are collected in full at
[`messages_dao.dart:185-194`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/messages_dao.dart#L185)
and passed straight into `isIn` at `:171`/`:176`; drift compiles one parameter
per element. The two maintenance callers both stop on *any* error:
`runOnce` returns at
[`maintenance.dart:76-79`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/maintenance.dart#L76)
before `rescheduleExpiry()`, and the expiry timer returns at
[`maintenance.dart:113-115`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/maintenance.dart#L113)
without rearming. The bound itself is SQLite's documented default
(`SQLITE_MAX_VARIABLE_NUMBER` = 32766 since 3.32); the bundled SQLCipher build's
flag was not queried, so a build compiled with the older 999 default would make
this trivial.

**Impact:** the delete fails every time it runs, so disappearing messages stay
on disk and in the UI, and because the failure precedes the remaining upkeep in
`runOnce`, `purgeExpiredDeferred`, `pruneProcessed` and the prekey/device
refreshes also stop for that engine's lifetime. Nothing self-heals: the due set
only grows, and a restart reaches the same failure on the first pass.

**Fix sketch:** never enumerate ids in Dart for a set write. `removeExpired` can
`DELETE FROM messages WHERE expires_at IS NOT NULL AND expires_at <= ?` and
recompute summaries for the distinct conversations it touched (or reuse a
`DELETE … RETURNING conversation_id`); `detachLocalMedia` can update through a
join on `messages` (it already has one to select). Where a caller really has
ids, chunk at ~500. No wire or schema change; engine behaviour unchanged.
Optionally make both maintenance callers rearm in a `finally`.
Test that proves it: insert 40,000 expired messages in one CTE (the style of
[performance_test.dart:25-48](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/test/performance_test.dart#L25)),
call `removeExpired`, expect no throw and zero rows left.

**Overlap:** AUD-10-2 (the same "build the list in Dart" habit), S10-1.

### AUD-10-2 `HistoryStore.backupableCount` emits `NOT IN ()` for an empty exclusion list, which SQLite rejects

**Severity:** P3
**Confidence:** confirmed
**Where:** [history_store.dart:42-66](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L42)
(the clauses at
[`:51-52`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L51),
`_marks` at
[`:66`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L66)).
Caller: [snapshot.dart:93-97](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/backup/snapshot.dart#L93).

**What:** `_marks(n)` returns `''` for `n == 0`, so an empty list produces
`kind NOT IN ()` — a syntax error in SQLite, not an empty-false predicate. The
query is a raw string built by interpolation, so nothing catches the shape at
compile time.

**Trigger:** any caller that passes no excluded kinds or statuses. The only
caller today passes two non-empty constants, so the bug is latent; it becomes
live if the export filter is ever made policy-driven (the method's own doc says
the caller owns that list), or if a test exercises the empty case.

**Evidence:** `_marks` at `:66`; `receiptsFor` right below guards its empty list
([`:86-87`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L86)),
`backupableCount` does not. `included()`
([snapshot.dart:80-88](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/backup/snapshot.dart#L80))
is the rule this count mirrors, and it has no such dependency.

**Impact:** a backup run fails before it starts (`countToExport` throws), so
export aborts with a database syntax error rather than a size. No data is lost;
the failure is loud.

**Fix sketch:** add each `AND … NOT IN (…)` clause only when its list is
non-empty (or emit `AND 1`), and keep the parameter order aligned; no schema or
wire change. Test that proves it: `backupableCount` with two empty lists returns
the number of messages a backup would keep (compare against `messageCount`
minus view-once and already-expired rows).

**Overlap:** S10-3 (raw SQL outside codegen), AUD-10-1.

### AUD-10-3 A thumbnail job converted to a download while a worker holds it is marked done by the thumbnail worker; the download never runs

**Severity:** P3
**Confidence:** likely
**Where:** [transfers_dao.dart:91-113](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/transfers_dao.dart#L91)
(`_enqueue` rewrites `kind`/`size`/`mediaKey` on the existing row and keeps
`state` when it is `inFlight`);
[download_runner.dart:244-250](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/transfers/download_runner.dart#L244)
(`runThumbnail` calls `markDone(job.id)` unconditionally);
[media_service.dart:177-202](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/transfers/media_service.dart#L177)
(`downloadNow` enqueues without looking at an in-flight job).

**What:** One job row is shared by an attachment's thumbnail and its full
download (the table allows one row per attachment). When the user asks for the
file while the thumbnail job is running, the row becomes a `download` job but
keeps the thumbnail worker's `inFlight` state and lease. That worker finishes,
then marks *its* job done — the converted download row — with offset 0 and no
local path. No worker will claim a done job, and the attachment was already set
to `downloading`, so the UI waits forever.

**Trigger:** tapping download in the window between the thumbnail job being
claimed and the thumbnail fetch finishing (a few KiB over the network, so
milliseconds to seconds). Narrow, not zero: the thumbnail is exactly what the
user is looking at when they decide to open the file.

**Evidence:** `_enqueue` preserves `state` only for `inFlight`
([`transfers_dao.dart:104-106`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/transfers_dao.dart#L104))
but overwrites the other identity columns unconditionally; `markDone` takes only
an id
([`transfers_dao.dart:322-330`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/transfers_dao.dart#L322))
so the caller cannot say which job it claimed. `downloadNow` writes the job and
the `downloading` attachment state in the same transaction
([`media_service.dart:191-201`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/transfers/media_service.dart#L191)),
and the thumbnail worker's read of the job predates it.

**Impact:** the requested download silently does not happen and the attachment
shows a permanent spinner; retrying (which re-enqueues) recovers it. No data
loss.

**Fix sketch:** make completion conditional on the claim, not just the id:
`markDone(id, kind:, lease:)` writing `WHERE id = ? AND kind = ? AND
lease_until = ?` (and warning/false when it changes nothing), or refuse to
convert an `inFlight` job and let `downloadNow` queue the download once the
lease ends. The first needs a lease/version token on a claimed job — see S10-2;
no wire change; the app needs nothing.

**Test that proves it:** claim the thumbnail job, call `enqueueDownload` for the
same attachment, then run the thumbnail completion; expect the job to be
`pending` with kind `download` (or the thumbnail worker to report that it lost
the job), not `done`.

**Overlap:** AUD-10-4 (one row, several consumers), S10-2.

### AUD-10-4 `enqueueStandalone` returns an old job for a reused purpose and keeps its stale path; `purpose` has no uniqueness

**Severity:** P3
**Confidence:** confirmed
**Where:** [transfers_dao.dart:62-80](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/transfers_dao.dart#L62),
[transfers.dart:56-61](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/tables/transfers.dart#L56),
pinned by [transfers_test.dart:100-131](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/test/transfers_test.dart#L100).

**What:** `enqueueStandalone` looks the purpose up and returns the existing id
without touching it. A reused purpose therefore keeps the *first* call's
`localPath`, `kind` and state — even when that job is already `done` — so a new
file (the changed group avatar, the next backup blob) is never uploaded. There
is also no unique key on `purpose`: `uniqueKeys` names only `attachmentRowid`,
and every standalone row has NULL there, which SQLite treats as distinct, so two
racing calls can create two rows for one purpose.

**Trigger:** the first production caller that reuses a purpose. Today none
exists: only tests call it (a search for `enqueueStandalone` in `lib/` finds the
declaration and the tests only), so the path is dead but exported and tested as
if supported.

**Evidence:** the doc comment promises "or returns the existing job for the same
purpose"; the test asserts the second call returns the first id **and** that the
stored path is still `media/avatar.bin`
([`transfers_test.dart:120-129`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/test/transfers_test.dart#L120)),
which is the bug written down as the contract. `_enqueue` (which does update a
reused row) is not used here. `remove()` deletes `localPath`
([`transfers_dao.dart:361-373`](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/transfers_dao.dart#L361)),
so duplicates that do share a path delete it under each other.

**Impact:** a future avatar/backup feature silently uploads the old file (or
nothing) on every change after the first; concurrent enqueues can produce two
jobs whose file one of them deletes. No impact today, because the method is
unused.

**Fix sketch:** decide the contract, then make it true: either delete
`enqueueStandalone` (and the `purpose` column) with its test, or make reuse an
update (`kind`, `localPath`, `attempts: 0`, state pending) and enforce it with a
unique index on `purpose` (schema 5, expand→migrate: add the index in a new step
after checking no duplicates exist). Test: a second call with a new path stores
the new path and is pending.

**Overlap:** AUD-10-3, S10-2.

## Structural proposals

### S10-1 Make "delete this set" a database statement, not a Dart list

**Current shape:** every bulk read/update in the package builds a Dart list of
ids and compiles it into `IN (?, …)` — `removeExpired`, `detachLocalMedia`,
`receiptsFor`, reactions, attachments — with the 32,766-parameter horizon and an
O(n) list on every pass.
**Hazard:** AUD-10-1: the operation fails outright above the limit, and the
failure is sticky because it recurs on the same set.
**Proposed shape:** set writes take a *query* (a `Selectable` or a SQL
predicate) and are issued as `DELETE … WHERE` / `UPDATE … WHERE` (drift's
`deleteWhere` or `customUpdate`), with a single shared chunking helper for the
few callers that genuinely receive ids from the UI.
**Migration path:** internal only (no schema, no wire); convert the four sites,
keep behaviour identical; no expand/contract needed.
**Risk:** low — the condition moves from Dart to SQL; the summary refresh after
`removeExpired` must still be per affected conversation.
**Size:** S.

### S10-2 Give a transfer job an immutable identity and a claim token

**Current shape:** `transfer_jobs` holds one row per attachment whose `kind` can
change under a running worker (thumbnail → download), and completion is by id
alone; three workers (upload, download, thumbnail) share the table and the lease
column without saying which kind they hold.
**Hazard:** AUD-10-3 (a worker completes a job that changed under it) and the
`attempts` reset in `_enqueue`
([transfers_dao.dart:107](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/transfers_dao.dart#L107)),
which lets repeated re-enqueues defeat the retry cap.
**Proposed shape:** `kind` is fixed once claimed; `claim()` returns (and stores)
a monotonically increasing `version`; `markDone`, `resume`/`setProgress` and
`fail` write `WHERE id = ? AND version = ?` and report a lost claim, the same
compare-and-set pattern `sessions`/`sender_keys` already use
([crypto_dao.dart:51-89](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/daos/crypto_dao.dart#L51)).
A download requested while a thumbnail runs is enqueued separately (or as a flag
the same claim honours) rather than re-identifying the row.
**Migration path:** expand: schema 5 adds `version INTEGER NOT NULL DEFAULT 0`
(the shape of steps 3 and 4); write the version on claim; migrate: only the
conversion sites change; contract: none needed (old rows at 0 are claimable).
**Risk:** medium — every worker completion path changes; a worker that ignores
the false return could silently drop progress, so the DAO's return value must be
checked where the job is closed.
**Size:** M.

### S10-3 Bring `HistoryStore` inside the DAO/codegen boundary

**Current shape:** whole-history access is a plain class issuing hand-written
SQL and drift selects over `HelixDb`
([history_store.dart:1-218](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/lib/src/history_store.dart#L1));
it duplicates rules the DAOs own (`receiptsFor` vs `MessagesDao.receiptsFor`,
`backupableCount` vs `snapshot.included`) and reads chunks directly instead of
through `TransfersDao`.
**Hazard:** raw strings are invisible to codegen and to the generated-column
checks, and `backupableCount` already shows the first symptom (AUD-10-2). The
backup/restore path touches *every* table, so a schema change that compiles
everywhere else can leave one query stale until a backup runs.
**Proposed shape:** make it a `@DriftAccessor` DAO (or fold each method onto its
owning DAO) so column names, types and parameter lists are generated; keep the
paging and merge semantics.
**Migration path:** no schema or wire change; a mechanical move plus regenerated
code, verified by the existing export/restore/transfer tests.
**Risk:** low for the type-checking win; the class is deliberately not a DAO
("adds nothing to the schema"), so the owner may prefer the lighter fix of
routing every method through a DAO that already exists.
**Size:** M.

## Coverage gaps

- No test drives any bulk set write above SQLite's parameter limit; the chunking
  path AUD-10-1 needs does not exist yet.
- `backupableCount` has no empty-list test, and the engine's pinning test
  compares it with `included()` only for the current non-empty filter
  ([snapshot.dart:90-97](file:///J:/Projects/helix/helix_remote/packages/helix_remote_engine/lib/src/backup/snapshot.dart#L90)).
- No test enqueues a download while a thumbnail job is claimed; the existing
  re-enqueue test covers only the state-preserving branch for the same upload.
- `enqueueStandalone` is exercised by tests only, and its test asserts the stale
  return that AUD-10-4 describes.
- Two-engine safety is tested by *sequencing* (`saveSessions` twice with the same
  expected version), never by two real connections racing; the guarantee rests
  on drift's `BEGIN IMMEDIATE` and the 5 s busy timeout, which no test
  exercises. `busy_timeout` itself is checked
  ([encryption_test.dart:92-98](file:///J:/Projects/helix/helix_remote/packages/helix_remote_db/test/encryption_test.dart#L92)).
- `wipeAll` on an encrypted file asserts data absence only; it does not test a
  second open connection (the FCM isolate) writing during the wipe, which is the
  real sign-out race.
